TCP and UDP

When to use TCP and when to use UDP

  • 1.5

What the transport layer adds

IP gets a packet to the right host. It does not say which application on that host should get it, and it does not promise the packet arrives. The transport layer (Layer 4) fills those gaps. It has two main protocols: TCP (Transmission Control Protocol) and UDP (User Datagram Protocol).

Ports pick the application

Both TCP and UDP use port numbers (0 to 65535). A server listens on a known port, for example 443 for HTTPS. The client picks a random high ephemeral port as its source. The pair of address and port at each end identifies one conversation, so a PC can hold many sessions to the same server at once.

Ports 0 to 1023 are the well-known ports, used by standard services.

TCP: reliable and ordered

TCP is connection-oriented. Before any data moves, the two ends set up a session with the three-way handshake:

  1. The client sends SYN (synchronise), with its starting sequence number.
  2. The server replies SYN-ACK: its own sequence number, and an acknowledgement of the client's.
  3. The client sends ACK. The session is open.

Every byte then has a sequence number. The receiver sends back acknowledgements. Anything not acknowledged in time is retransmitted, and the receiver puts segments back in order. Windowing lets the receiver say how much data it can take before the sender must wait for an acknowledgement, which is TCP's flow control. The session is closed with FIN messages.

UDP: light and fast

UDP is connectionless. There is no handshake, no sequence numbers, no acknowledgements and no retransmission. Its header is 8 bytes, against at least 20 bytes for TCP. If a datagram is lost, UDP does nothing about it; the application decides whether to care.

That suits traffic where a late packet is useless anyway. A voice or video call would rather skip a lost moment than wait for a resend. It also suits short question-and-answer exchanges such as DNS lookups, where the application can simply ask again.

Which uses which

  • TCP: HTTP 80, HTTPS 443, SSH 22, Telnet 23, FTP 20 and 21, SMTP 25.
  • UDP: DHCP 67 and 68, TFTP 69, NTP 123, SNMP 161 and 162, syslog 514, voice and video media.
  • DNS: port 53, normally UDP for queries, and TCP for large responses and zone transfers.

The rule of thumb: if every byte must arrive intact and in order, as with a file or a web page, use TCP. If speed matters more than perfection, or the exchange is one small packet each way, use UDP.

Reliability in action

  1. A PC downloads a file over TCP. The server sends four segments in a row, because the PC's window allows that much before an acknowledgement is needed.
  2. The third segment is lost on the way. The PC receives the first, second and fourth.
  3. The PC acknowledges only up to the end of the second segment, which tells the server where the gap starts. It holds the fourth segment rather than passing it to the application out of order.
  4. The server resends the third segment. The PC now has everything, acknowledges up to the end of the fourth, and hands the data to the application in the right order.

With UDP the same loss would simply leave a gap. Nothing in the protocol notices it.

Side by side

  • Session: TCP opens one with a handshake; UDP just sends.
  • Delivery: TCP acknowledges and resends; UDP is best effort.
  • Order: TCP reorders by sequence number; UDP passes datagrams up as they arrive.
  • Flow control: TCP uses windowing; UDP has none.
  • Overhead: TCP has a larger header and extra messages; UDP has an 8-byte header and nothing else.

Seeing it on a device

On a PC, netstat -an lists open TCP and UDP sessions with local and remote ports. On a Cisco router, show tcp brief lists TCP sessions to the device itself, such as an SSH login, and show control-plane host open-ports lists the ports it is listening on.

Key terms

Port number
A 16-bit number that identifies the application a segment belongs to.
Ephemeral port
A temporary high port a client picks as its source for one session.
Three-way handshake
SYN, SYN-ACK, ACK: the exchange that opens a TCP session.
Sequence number
A TCP counter that numbers the bytes sent, so the receiver can reorder and detect loss.
Acknowledgement
A TCP message confirming which data has arrived.
Windowing
TCP flow control: the receiver says how much data may be sent before an acknowledgement.
Connectionless
Sending without first setting up a session, as UDP does.

For the exam

  • 1.5: compare TCP to UDP.
  • TCP: connection-oriented, three-way handshake, sequencing, acknowledgements, retransmission, windowing (flow control). UDP: none of these.
  • UDP header 8 bytes; TCP header at least 20 bytes.
  • Know the common ports and which protocol each uses: DHCP 67/68 UDP, TFTP 69 UDP, SNMP 161 UDP, syslog 514 UDP, NTP 123 UDP, SSH 22 TCP, HTTPS 443 TCP.
  • Voice and video use UDP because retransmitted audio would arrive too late to be useful.

Common mistakes

  • Saying UDP is unreliable so it is worse: it is chosen on purpose where speed and low overhead matter more.
  • Writing an ACL that permits DNS only on TCP 53: ordinary lookups use UDP 53 and fail.
  • Mixing up TFTP and FTP: TFTP uses UDP 69 with no login; FTP uses TCP 20 and 21.
  • Thinking the client uses the well-known port too: the client uses a random ephemeral port; only the server side is well known.

Quick check

1. What is the correct order of the TCP three-way handshake?

  1. SYN, ACK, SYN-ACK
  2. ACK, SYN, SYN-ACK
  3. SYN, SYN-ACK, ACK
  4. SYN, SYN, ACK
Show the answer

C. SYN, SYN-ACK, ACK

The client sends SYN, the server answers SYN-ACK, and the client confirms with ACK. Only then does data flow.

2. Why does voice traffic use UDP rather than TCP?

  1. A retransmitted voice packet would arrive too late to be played, so recovery is pointless
  2. UDP encrypts the audio
  3. UDP guarantees delivery in order
  4. TCP cannot carry more than one call at a time
Show the answer

A. A retransmitted voice packet would arrive too late to be played, so recovery is pointless

Real-time audio cannot wait for resends. UDP's low overhead and lack of retransmission suit it; a small loss is barely heard.

3. Which TCP feature lets a receiver limit how much data the sender may send before waiting for an acknowledgement?

  1. Sequencing
  2. Windowing
  3. The checksum
  4. The three-way handshake
Show the answer

B. Windowing

Windowing is TCP's flow control. Sequence numbers handle order and loss detection, not the amount in flight.

4. Which of these services runs over UDP?

  1. SSH
  2. HTTPS
  3. Telnet
  4. TFTP
Show the answer

D. TFTP

TFTP uses UDP port 69. SSH (22), HTTPS (443) and Telnet (23) all run over TCP.

5. A PC opens two browser tabs to the same web server. How does it keep the two sessions apart?

  1. Each tab uses a different server port
  2. Each session has a different client source port
  3. Each tab uses a different IP address
  4. TCP sends both on one session
Show the answer

B. Each session has a different client source port

The client picks a different ephemeral source port for each session. The server port (443) stays the same.
