DHCP snooping

How a switch stops fake DHCP servers

  • 5.7Layer 2 security

The problem: anyone can answer

DHCP is first come, first served. A client broadcasts a Discover and takes the first Offer it gets. It has no way to tell a real server from a fake one.

In this lab, ROGUE, a laptop on Fa0/5, runs its own DHCP server. It is on the same switch as the clients, so it answers before R1. It names itself as the default gateway, so the clients send all their traffic to it. That is either a man-in-the-middle attack or, at best, an outage. A rogue server is not always malicious: a home router plugged in by a user does the same damage.

Trusted and untrusted ports

DHCP snooping makes the switch inspect DHCP messages in the VLANs you choose. Each port is trusted or untrusted, and every port is untrusted by default.

  • Client messages (Discover, Request) are allowed in on any port.
  • Server messages (Offer, Acknowledge) are allowed in only on trusted ports. If one arrives on an untrusted port, it is dropped.

So you trust only the ports that lead toward the real server: here SW1 Gi0/1, the uplink to R1. ROGUE's offers are dropped at Fa0/5 and never reach a client.

The binding table

As leases are handed out, the switch records each one in the DHCP snooping binding table: MAC address, IP address, lease time, VLAN and port. Snooping itself only needs it to check later messages, such as a release, against the right port. Other features use it too: Dynamic ARP Inspection checks ARP against it.

Hosts with fixed addresses never appear in it, because they never ask for a lease. That is fine for snooping, but it matters as soon as a feature such as DAI relies on the table.

The option 82 surprise

When snooping is on, a Cisco switch adds option 82 to client requests by default. Option 82 records which switch and port the request came from. But SW1 is not a relay, so the request carries option 82 while its relay address field (giaddr) is still 0.0.0.0. A Cisco IOS DHCP server treats that combination as suspicious and drops it, so R1 stays silent.

In this lab the fix is no ip dhcp snooping information option on SW1. Telling R1 to trust option 82 would also work.

How it is set up and checked

Turn it on globally with ip dhcp snooping, then for VLAN 10 with ip dhcp snooping vlan 10. Both are needed. Then ip dhcp snooping trust on Gi0/1. show ip dhcp snooping shows the VLANs, the trusted ports and the option 82 setting. show ip dhcp snooping binding should list PC1 and PC2 with their port. User ports can also be given ip dhcp snooping limit rate, to stop one host flooding the server with requests.

See it happen

In the app, these steps play out as packets moving across the lab's map.

  1. PC1 asks for an address PC1 broadcasts a Discover. SW1 floods it out every port in VLAN 10, so it reaches both R1 and ROGUE.
  2. Before snooping ROGUE answers first and names itself, 192.168.10.250, as the gateway. PC1 accepts it and cannot reach 203.0.113.10.
  3. Snooping on, Fa0/5 untrusted Now the rogue's Offer arrives on an untrusted port. Server messages are not allowed there, so SW1 drops it.
  4. The real server stays silent SW1 adds option 82 with no relay address to PC1's request. R1 treats that as inconsistent and drops it.
  5. Option 82 off: R1 answers With the option turned off, R1 answers. Its Offer enters SW1 on trusted Gi0/1, so it is allowed through to PC1.
  6. The lease is recorded When R1's Ack passes, SW1 records PC1's MAC, IP, VLAN 10 and port Fa0/1 in its binding table.

Key terms

DHCP snooping
A switch feature that filters DHCP messages so only trusted ports can carry server replies.
Trusted port
A port allowed to deliver DHCP server messages. Usually the uplink toward the real server.
Untrusted port
A port where server messages are dropped. Every port is untrusted by default.
Rogue DHCP server
An unauthorised device handing out addresses, often naming itself as the gateway.
Binding table
The switch's list of leases: MAC, IP, lease, VLAN and port.
Option 82
DHCP relay agent information: which switch and port a request came from.

For the exam

  • 5.7: configure and verify Layer 2 security features: DHCP snooping, dynamic ARP inspection, and port security.
  • Server messages (Offer, Ack) are dropped on untrusted ports. Client messages are allowed.
  • All ports are untrusted by default. Trust the uplinks toward the server.
  • Snooping must be enabled globally and per VLAN.
  • The binding table feeds Dynamic ARP Inspection.

Common mistakes

  • Enabling snooping without trusting the uplink: every legitimate offer is dropped and nobody gets an address.
  • Enabling it globally but not for the VLAN: nothing is inspected, and the rogue still wins.
  • Option 82 left on with a Cisco router as the server: requests reach R1 but it never answers.
  • Trusting user ports "to be safe": a trusted port lets a rogue server through.

Quick check

1. With DHCP snooping on, which message is dropped when it arrives on an untrusted port?

  1. Discover
  2. Request
  3. Offer
  4. Release from the same host
Show the answer

C. Offer

Offers and Acks are server messages and only pass trusted ports. Discover and Request come from clients and are allowed.

2. Snooping is on and Gi0/1 is trusted, but R1 never answers. What fits best?

  1. Option 82 is being inserted and the Cisco server drops the request
  2. The rogue is still winning
  3. The client ports must be trusted
  4. The binding table is full
Show the answer

A. Option 82 is being inserted and the Cisco server drops the request

The switch adds option 82 with no relay address, and an IOS DHCP server drops that by default. Turning the option off on the switch fixes it.

3. Which port on SW1 should be trusted?

  1. Fa0/5, so you can monitor the rogue
  2. Every port
  3. Fa0/1 and Fa0/2, where the clients are
  4. Gi0/1, toward R1
Show the answer

D. Gi0/1, toward R1

Trust only the path toward the legitimate server. Trusting client ports would let any server on them through.

4. What does the snooping binding table record?

  1. Only the rogue servers seen
  2. MAC, IP, VLAN, lease and port for each lease
  3. Every ARP reply
  4. The DHCP pools on R1
Show the answer

B. MAC, IP, VLAN, lease and port for each lease

Each lease that passes is recorded with its port. Dynamic ARP Inspection uses this table next.
