Wiring a wireless LAN

How an access point joins its controller

  • 1.1Network components

  • 2.8Device management access

Two ways to run Wi-Fi

An autonomous access point is a complete Wi-Fi device: you configure each one by itself and it needs a trunk carrying every client VLAN. In a controller-based design the access points are lightweight: the wireless LAN controller (WLC) holds the configuration, and every AP tunnels its clients back to the controller. You build a WLAN once, on the controller, and every AP serves it. Harbor Street chose a controller, so the wiring in this lab is the controller-based kind.

CAPWAP: the tunnel between AP and controller

A lightweight AP finds its controller, then opens two CAPWAP tunnels to it over the wired network: control on UDP 5246, data on UDP 5247. Control carries the AP's configuration, its radio settings and statistics. Data carries the wireless clients' frames. A client associated with AP1 does not enter the switch on AP1's port as a normal frame; it travels inside the data tunnel to the controller, which drops it into the VLAN mapped to that WLAN.

That is why the AP needs only one thing from the wire: an IP address in the management network and a path to the controller's management address. If UDP 5246 cannot get through, the AP never joins and no radio turns on.

Which port is which

  • The AP's port is an access port in the management VLAN (VLAN 10 here). Client VLANs do not need to exist on it. PortFast suits it: a single device, no loop risk.
  • The controller's port is a trunk, because the controller must place clients into VLAN 20 (staff) or VLAN 30 (guest). Its management interface can be tagged, or untagged as in this lab; untagged means it must be the trunk's native VLAN.
  • The router's port is a trunk too, so the router can hold the gateway for every VLAN on one subinterface each.

Larger controllers bundle several ports into a LAG (an EtherChannel) for bandwidth and redundancy; one trunk is enough here.

How the AP finds the controller

In the real world the AP usually gets its address by DHCP in the management VLAN, and learns the controller's address from DHCP option 43, from a DNS name (cisco-capwap-controller), from a broadcast on its own subnet, or from an address saved earlier. In this lab the AP has a fixed address, so the join path is simply: AP1 to its gateway, AP1 to 10.10.10.2 on UDP 5246 and 5247. If the AP and controller are in different subnets, the router must route between them and nothing on the way may block those ports.

Managing the controller

Administrators reach the controller's web page over HTTPS (TCP 443) and its command line over SSH (TCP 22) at the management address. That is where the WLANs are built: name (SSID), security such as WPA2 with a pre-shared key, and the interface (VLAN) each WLAN maps to. The exam expects you to recognise those GUI steps; here the admin PC in VLAN 10 proves it can open the page.

Check it worked

show vlan brief shows the three VLANs and Fa0/1 and Fa0/2 in VLAN 10. show interfaces trunk shows Gi0/1 with native VLAN 10 and Gi0/2 with native VLAN 1, both allowing 10, 20 and 30. From AP1, ping 10.10.10.1 and 10.10.10.2. From PC1, telnet 10.10.10.2 443 opens: the controller's page is reachable.

See it happen

In the app, these steps play out as packets moving across the lab's map.

  1. The access point on its access port AP1 sends frames untagged. SW1 puts them in VLAN 10, the management VLAN, because Fa0/1 is an access port there.
  2. The join request AP1 asks the controller to join on UDP 5246. The frame leaves SW1 on the Gi0/1 trunk untagged, because VLAN 10 is the native VLAN there, which is how the controller's untagged management interface expects it.
  3. The controller answers The controller accepts the AP and pushes its configuration down the control tunnel. Only now do the radios switch on.
  4. A wireless client's traffic A staff laptop's frames travel inside the data tunnel to the controller, which places them in VLAN 20 on its trunk. The switch port of the AP never sees VLAN 20.
  5. Out to the gateway From the controller the frame crosses the trunk tagged 20 to R1's subinterface G0/0.20, the gateway for the staff WLAN.
  6. The admin builds the WLAN PC1 opens the controller's web page in VLAN 10. The SSID, WPA2 pre-shared key and the mapping to VLAN 20 are set there, not on the switch.

Key terms

Lightweight access point
An AP that takes its configuration from a controller and tunnels its clients to it.
Wireless LAN controller (WLC)
The device that configures and manages lightweight APs and places their clients into VLANs.
CAPWAP
The protocol between AP and controller: control on UDP 5246, data on UDP 5247.
Management interface
The controller's address used by APs to join and by admins to log in.
Dynamic interface
A controller interface mapped to a client VLAN; each WLAN is tied to one.
Native VLAN
The VLAN whose frames cross a trunk untagged.
LAG
A bundle of controller ports acting as one link, like an EtherChannel.

For the exam

  • 5.10: configure a WLAN with WPA2 PSK in the controller GUI: WLAN name, security, interface mapping.
  • A lightweight AP's switch port is an access port in the management VLAN; an autonomous AP needs a trunk.
  • CAPWAP ports: 5246 control, 5247 data, both UDP.
  • AP modes: local serves clients; monitor, sniffer and rogue detector do not.

Common mistakes

  • Trunking the lightweight AP's port "to be safe": it works, but the AP uses only the native VLAN, and an untagged management VLAN mismatch leaves it unable to join.
  • Forgetting the client VLANs on the controller trunk: APs join, clients associate, and then get no DHCP and no gateway.
  • Blocking UDP 5246 or 5247 between AP and controller with an ACL: the AP shows as never joined with no obvious error on the switch.
  • Putting the controller's untagged management interface on a trunk whose native VLAN is 1: the controller ends up in the wrong VLAN.

Quick check

1. Which switch port configuration does a lightweight access point need?

  1. A trunk carrying every client VLAN
  2. An access port in the management VLAN
  3. A routed port
  4. An EtherChannel to the controller
Show the answer

B. An access port in the management VLAN

Its clients ride inside the CAPWAP tunnel, so the AP needs only the management VLAN. An autonomous AP would need the trunk.

2. CAPWAP uses which ports?

  1. TCP 5246 and 5247
  2. UDP 5246 (control) and 5247 (data)
  3. UDP 67 and 68
  4. TCP 443 and 22
Show the answer

B. UDP 5246 (control) and 5247 (data)

Both tunnels are UDP: 5246 carries control, 5247 carries client data. 443 and 22 are for managing the controller.

3. The controller's management interface is untagged. What must be true of its switch trunk?

  1. The native VLAN must be the management VLAN
  2. The trunk must allow only VLAN 1
  3. DTP must be enabled
  4. The port must be an access port
Show the answer

A. The native VLAN must be the management VLAN

Untagged frames on a trunk belong to the native VLAN, so the native VLAN must be the management VLAN or the controller lands in the wrong VLAN.

4. An AP has an address and can ping the controller, but never joins. Which is the most likely cause?

  1. The AP port is in the wrong VLAN
  2. UDP 5246 is blocked between them
  3. The controller trunk lacks VLAN 20
  4. The AP has no default gateway
Show the answer

B. UDP 5246 is blocked between them

Ping proves addressing and routing. A blocked control port stops the join itself; a missing client VLAN would affect clients after the join.

5. Where is a WLAN with WPA2 PSK created in a controller-based design?

  1. On each access point
  2. On the switch, per VLAN
  3. In the controller's web interface
  4. On the router subinterface
Show the answer

C. In the controller's web interface

The controller holds the WLAN definitions (SSID, security, interface) and pushes them to every lightweight AP.
