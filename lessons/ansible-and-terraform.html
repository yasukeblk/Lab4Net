Ansible and Terraform

How Ansible and Terraform manage configuration

  • 6.6

The problem: keeping many devices right

Automation is more than a script that changes one setting. Configuration management tools keep many devices in a known, intended state. The intended configuration is written in text files, stored in version control such as Git, reviewed like code, and applied by the tool. This approach is called infrastructure as code.

The gain is that the files become the record of truth. If a device drifts, the tool can put it back. If a change breaks something, the previous version of the files shows exactly what to return to.

Ideas the tools share

  • Idempotent: running the same task twice gives the same result as running it once. If a VLAN already exists, the tool reports no change instead of creating it again. That makes it safe to run the tool repeatedly.
  • Agent or agentless: an agent is software installed on each managed device. Agentless tools connect using what the device already has, such as SSH or an API. Most network devices cannot run third-party agents, so agentless tools suit them.
  • Push or pull: in a push model a central server sends changes out. In a pull model each device checks in and fetches its configuration.
  • Declarative means you describe the end state you want. Procedural (imperative) means you list the steps to get there.

Ansible

Ansible, from Red Hat, is agentless and uses a push model. It runs on a control node and connects to devices over SSH (or an API). It is written in Python.

  • The inventory lists the devices to manage, often grouped, for example all access switches.
  • A playbook is a file written in YAML. It holds one or more plays, each made of tasks that run in order, top to bottom.
  • Each task calls a module, a piece of code that does one job, such as sending IOS configuration lines or gathering facts.
  • Templates written in Jinja2 build per-device configuration from shared variables.

A playbook is run with ansible-playbook. Because the tasks run in the order written, Ansible is usually described as procedural, although many of its modules are themselves idempotent.

Terraform

Terraform, from HashiCorp, is an infrastructure-as-code tool that is strongly declarative. You write configuration files in HCL (HashiCorp Configuration Language) describing the resources that should exist, and Terraform works out what to create, change or delete, and in what order.

  • Providers are plugins that let Terraform talk to a platform through its API: a cloud, a controller or a device family.
  • The state file records what Terraform has built, so it can compare the real world with the configuration.
  • The workflow is terraform init (get the providers), terraform plan (show what would change), terraform apply (make the changes) and, when finished, terraform destroy.

Terraform is agentless and works through APIs. It is widely used for building cloud infrastructure, and increasingly for networks.

Choosing between them

The two often work together. Terraform is strongest at provisioning: creating the infrastructure, such as cloud networks, virtual routers and firewall rules. Ansible is strongest at configuring what already exists, such as pushing interface and routing configuration to a fleet of switches over SSH.

Older exams also covered Puppet and Chef. Both are usually agent-based and pull-based, which is one reason they fit network devices less well than agentless tools.

A typical change, start to finish

  1. An engineer edits the files: for example, adds VLAN 30 to the variables for the access switches.
  2. The change is committed to Git and reviewed by a colleague, who can see exactly which lines changed.
  3. The tool is run in a check mode first: terraform plan, or Ansible's check mode, to show what would change.
  4. The tool applies the change to every device in the group.
  5. Running it again reports no changes, which confirms every device now matches the files.

Key terms

Infrastructure as code
Defining infrastructure and configuration in version-controlled text files that a tool applies.
Idempotent
Running a task again gives the same result and makes no further change.
Agentless
Managing a device without installing software on it, using SSH or an API.
Playbook
An Ansible file in YAML that lists tasks to run against devices.
Inventory
The Ansible list of managed devices and their groups.
Module
The unit of Ansible code a task calls to do one job.
HCL
HashiCorp Configuration Language, used to write Terraform files.
Provider
A Terraform plugin that talks to one platform's API.
State file
Terraform's record of the resources it manages.

For the exam

  • 6.6: recognize the capabilities of configuration management mechanisms, such as Ansible and Terraform.
  • Ansible: agentless, push, SSH, YAML playbooks, inventory, modules, written in Python.
  • Terraform: declarative, HCL files, providers, state file, plan then apply.
  • Know what idempotent means and why it makes a tool safe to run again.
  • Puppet and Chef are typically agent-based and pull-based, in contrast to Ansible.

Common mistakes

  • Saying Ansible needs an agent on each switch: it does not, it connects over SSH from the control node.
  • Mixing up the file formats: Ansible playbooks are YAML, Terraform files are HCL.
  • Running terraform apply without reading the plan: a resource renamed in the files can be destroyed and recreated.
  • Editing devices by hand after adopting the tool: the files no longer match reality, and the next run overwrites the manual change.

Quick check

1. Which statement describes Ansible?

  1. Agent-based and pull-based, with manifests in Ruby
  2. Agentless and push-based, with playbooks in YAML
  3. Declarative, with files in HCL and a state file
  4. Agent-based, using SNMP to push changes
Show the answer

B. Agentless and push-based, with playbooks in YAML

Ansible pushes from a control node over SSH with no agent, and its playbooks are YAML. HCL and the state file belong to Terraform.

2. A task to create VLAN 10 runs on a switch that already has VLAN 10. The tool reports no change. What property is this?

  1. Idempotence
  2. Statelessness
  3. Encapsulation
  4. Redundancy
Show the answer

A. Idempotence

An idempotent task checks the current state and only acts if it differs, so running it again changes nothing.

3. What does terraform plan do?

  1. Installs the providers
  2. Deletes every resource it manages
  3. Pushes YAML playbooks to the devices
  4. Shows what Terraform would change, without changing anything
Show the answer

D. Shows what Terraform would change, without changing anything

plan compares the configuration with the state and reports the changes. apply makes them, init installs providers and destroy removes resources.

4. What is Terraform's state file for?

  1. It stores passwords for SSH logins
  2. It lists the tasks to run in order
  3. It records which resources Terraform has built, so it can compare them with the configuration
  4. It holds the YAML inventory of devices
Show the answer

C. It records which resources Terraform has built, so it can compare them with the configuration

The state file is how Terraform knows what already exists. Without it, Terraform could not work out what to add, change or remove.
